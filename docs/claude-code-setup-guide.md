# Claude Code 4層セットアップ 手順書（テストフォルダ版）

PCで、捨ててもいいテストフォルダの中に Claude Code の設定を一通り作って、
挙動を確かめるための手順書です。上から順にやれば動きます。

**進め方の目安：STEP 1〜2 が本命。STEP 3 以降は「やってみたければ」でOK。**

---

## いちばん大事な注意

Claude Code の設定には **個人用（全プロジェクト共通）** と **プロジェクト用** の2種類があります。

| 種類 | 場所 | 効く範囲 |
|---|---|---|
| 個人用 | `~/.claude/` | すべてのプロジェクト |
| プロジェクト用 | `そのフォルダ/.claude/` | そのフォルダの中だけ |

**この手順書で触るのは、プロジェクト用（テストフォルダの中の `.claude/`）だけです。**

理由：`~/.claude/skills/` には既に buzz-post、shindan-page、note-complete-machine など
20個以上のスキルが入っています。ここを練習でいじると、note作成もYouTube企画も
Threadsのリサーチも、全部の作業に影響が出ます。

**迷ったときのルール：`~/` から始まるパスは触らない。**

---

## STEP 0 — テストフォルダを作る

ターミナル（Macなら「ターミナル」、Windowsなら PowerShell）を開いて：

```bash
mkdir ~/cc-test
cd ~/cc-test
git init
claude
```

`git init` は必須ではありませんが、やっておくと
「設定をいじる前の状態」に戻せるので入れておきます。

起動したら、まず現状確認：

```
/doctor
```

設定ファイルがどこにあるか、何が読み込まれているかが出ます。
この時点ではほぼ空のはずです。

## STEP 1 — CLAUDE.md（チートシートの L1）★最優先

### これは何か

プロジェクトの説明書です。セッション開始時に**自動で読まれます。**
「これは何のプロジェクトか」を毎回説明しなくて済むようになります。

4層のなかで、**費用対効果がダントツで高いのはここです。**
他を全部飛ばしてもいいので、これだけは作ってください。

### やること

テストフォルダに、何か中身を1つ置きます（空だと書くことがないので）。
たとえば `index.html` を1枚作る、でも構いません。

そのうえで Claude Code の中で：

```
/init
```

フォルダの中身をスキャンして、`CLAUDE.md` のたたき台を作ってくれます。

### 中身を自分で直す

自動生成されたものは骨組みです。ここに手で足すと効きます：

```markdown
# このプロジェクトについて

オンライン秘書のタイプ診断ページ。1枚のHTMLで完結。

## 触ってはいけないもの
- 診断ロジック（scoreCalc 関数）は仕様確定済み。相談なしに変えない

## デザインルール
- 色は :root の CSS変数だけを使う。直接カラーコードを書かない
- フォントは Noto Sans JP / Noto Serif JP

## 公開手順
- GitHub Pages。main にpushで自動反映
```

### コツ

- **200行以内に収める。** 長すぎると要点がぼやけます
- 「やってほしいこと」より **「やってほしくないこと」** を書くほうが効きます
- 完璧を目指さない。作業していて「あ、また同じ説明した」と思ったら足す、で育てます

### 確認方法

Claude Code を一度終了して、もう一度 `claude` で起動します。
起動時に CLAUDE.md が読み込まれた表示が出れば成功です。

## STEP 2 — permissions（チートシートの 08）

### これは何か

「確認なしで実行していいこと／絶対にやってはいけないこと」の設定です。
毎回出る許可のポップアップを減らせます。

### やること

Claude Code の中で：

```
/permissions
```

対話画面で追加・削除できます。**手でJSONを書くより、こちらが安全です。**

### 参考：出来上がるファイル

`~/cc-test/.claude/settings.json`

```json
{
  "permissions": {
    "allow": [
      "Read",
      "Bash(git status)",
      "Bash(git diff:*)",
      "Write(*.md)"
    ],
    "deny": [
      "Bash(rm -rf:*)",
      "Read(.env)"
    ]
  }
}
```

### コツ

- `allow` は**狭く**始める。広げるのは後からいくらでもできます
- `deny` に `Read(.env)` を入れておくと、APIキーなどを誤って読まれません
- `settings.json` はGitに入れてOK。`settings.local.json` は自分専用（Gitに入れない）

## STEP 3 — Skills（チートシートの 06）

### これは何か

決まった作業手順のパックです。

### ちほさんの場合

**個人スキルとして既に20個以上お持ちなので、この層はもう完成しています。**
新しく作る練習をするなら、プロジェクト用として作ってください。

### やること（練習する場合）

```
~/cc-test/.claude/skills/test-skill/SKILL.md
```

というファイルを作ります。中身：

```markdown
---
name: test-skill
description: テスト用のスキル。「テストして」と言われたら必ずこのスキルを使うこと。
---

# テストスキル

呼ばれたら、以下を順にやる。

1. 「スキルが呼ばれました」と表示する
2. フォルダの中のファイル一覧を出す
```

`---` で囲まれた部分（frontmatter）が必須です。
特に `description` が、**いつ呼ばれるかを決める一番大事な部分**です。

### 確認方法

Claude Code を再起動して「テストして」と打ちます。
スキルが呼ばれれば成功です。呼ばれなかったら `description` に
トリガーになる言葉を増やします。

### コツ

- `description` に「〜と言われたら必ずこのスキルを使うこと」と書くと発動しやすくなります
- 手順は箇条書きで。長文の説明より、番号付きの手順のほうが確実に守られます

## STEP 4 — Hooks（チートシートの 07）★ここだけ慎重に

### これは何か

「特定のタイミングで、決まったコマンドを自動実行する」仕組みです。

**注意：これは実際にコマンドを実行します。** 書き方を間違えると
ファイルを壊す可能性があります。**テストフォルダでやる意味が一番あるのがここです。**

### やること

手でJSONを書かず、まず：

```
/hooks
```

対話画面で設定できます。

### まず試すなら、これ（何も壊さない例）

「Bashコマンドが実行される前に、メッセージを出すだけ」のフックです。

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "echo '[hook] Bashが実行されます'",
            "timeout": 5
          }
        ]
      }
    ]
  }
}
```

### 終了コードの意味

| コード | 意味 |
|---|---|
| 0 | 許可（そのまま実行される） |
| 2 | ブロック（実行させない） |

「危険なコマンドを止める」フックを作るなら、条件に合ったときに
`exit 2` を返すスクリプトを書きます。

### 主なタイミング

| 名前 | いつ動くか |
|---|---|
| `PreToolUse` | ツールを使う直前 |
| `PostToolUse` | ツールを使った直後 |
| `SessionStart` | セッション開始時 |
| `Stop` | 応答が終わったとき |

### コツ

- **hookを編集したら、`/hooks` で確認するか、Claude Code を再起動してください。**
  安全のため、起動時の内容が使われる作りになっています
- 最初は `echo` だけの無害なものから。いきなりファイルを消すコマンドを書かない
- `timeout` は必ず入れる。無限に待つ事故を防げます

## STEP 5 — Agents（チートシートの 09 / L4）

### これは何か

専門役のサブAIです。「レビュー担当」「調査担当」に分けて仕事を任せられます。

### 正直な話

**1ファイルだけのプロジェクトには、ほぼ効果がありません。**
分担させる仕事がないからです。

効いてくるのは、ファイルが何十個もあって
「全部読ませると長すぎる」ような規模になってからです。

練習として触るのは自由ですが、
**「今すぐ必要なもの」ではない**と思っておいてください。

### やること（練習する場合）

```
/agents
```

対話画面で作れます。ファイルとしては
`~/cc-test/.claude/agents/<名前>.md` に置かれます。

---

## 失敗したときの戻し方

### 設定だけ消したい

```bash
cd ~/cc-test
rm -rf .claude
```

`.claude` フォルダごと消せば、設定前の状態に戻ります。

### Hookが暴走している / 起動がおかしい

いったん Claude Code を終了して、`.claude/settings.json` の
`"hooks"` の中身を `{}` にしてから起動し直します。

### 全部やり直したい

```bash
rm -rf ~/cc-test
```

テストフォルダごと消します。**これが、テストフォルダでやる最大のメリットです。**

---

## 本番プロジェクトに移すとき

テストで動きが確認できたら、本番のリポジトリにコピーします。

```bash
cp -r ~/cc-test/.claude ~/本番のフォルダ/
cp ~/cc-test/CLAUDE.md ~/本番のフォルダ/
```

**そのままコピーせず、CLAUDE.md の中身は本番プロジェクトの内容に書き換えてください。**
テスト用の記述が残っていると、的外れな前提で作業されます。

チームで使うなら `.claude/settings.json` と `CLAUDE.md` は
Gitにコミットします（`settings.local.json` は個人用なので除外）。

## まとめ：どこから手をつけるか

| 優先度 | 層 | 理由 |
|---|---|---|
| ★★★ | CLAUDE.md | 効果が一番大きい。これだけでも十分価値がある |
| ★★ | permissions | 確認ポップアップが減って作業が軽くなる |
| ★ | Skills | 個人スキルで既に足りている。練習として |
| ★ | Hooks | 面白いが、テストフォルダ以外では慎重に |
| — | Agents | 今の規模だと出番がない |

**1日で全部やろうとしないこと。** STEP 1 だけ今日やって、
「思ったより効くな」と感じたら次に進む、くらいのペースで十分です。
